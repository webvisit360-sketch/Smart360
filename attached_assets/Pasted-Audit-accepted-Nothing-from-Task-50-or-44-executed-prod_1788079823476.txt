1 · ONE RUN PER TENANT IS WRONG — creator_runs_one_per_tenant_uq
A rerun of step 3 is a designed feature, not an accident. The entire rejection
memory exists because runs repeat: the specification says a rerun must never
re-propose what was already rejected, which presumes there is a rerun.

With this unique index a second run is either impossible or overwrites the
first, taking its report, token counts and cost with it. Then we cannot
compare two runs, cannot show a tenant's run history, and cannot answer "what
did the previous run cost" after the fact.

Replace it with:
· many runs per tenant, ordered by created_at;
· a partial unique index allowing at most ONE run in status 'running' per
  tenant, so two runs cannot execute concurrently for the same tenant.
That gives the protection the index was reaching for without destroying
history.
