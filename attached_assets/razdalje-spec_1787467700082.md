# AUTOMATIC DISTANCES — spec (owner-approved)

Goal: fill `distanceMeters` for the tenant's nearby places without the host
typing 73 values, and without any paid service or subscription.

Owner decision: compute automatically, then let the host REVIEW and correct
in one list. Nothing is published to guests until the host approves the row.

Hard constraints:
- No paid services, no subscriptions, no API keys that cost money.
- Never invent or estimate a distance. A row we cannot resolve stays empty
  and the guest card simply renders without a distance.
- Straight-line distance is NOT an acceptable substitute for road distance.
  If road routing fails, the row stays unresolved.
- The host's manual value always wins and is never overwritten.

---

## Pipeline (one-time per place, then cached)

1. **Source of location**, in this order:
   a. an explicit Google Maps link stored on the item → extract coordinates
      from it (no external call);
   b. coordinates already stored on the item;
   c. the legacy map-query text (all 73 Meli Pu places have this) →
      geocode once via a free OpenStreetMap service (Nominatim), respecting
      its usage policy: a descriptive User-Agent identifying Smart360, at
      most 1 request per second, and results cached permanently.
2. **Road distance and driving time** from the tenant's coordinates to the
   place's coordinates via a free routing service (public OSRM). Cache the
   result; recompute only when a link, coordinates or the tenant's own
   coordinates change.
3. Store: resolved coordinates, road distance in metres, driving minutes,
   the source used (link / coordinates / geocoded), and a confidence flag.

## Review screen (the part that protects us)

Because geocoding by name can resolve to the wrong building — exactly what
happened to the tenant's own address — nothing goes live unproposed:

- A list in the admin: one row per place with the proposed distance and
  driving time, the resolved address as returned by the geocoder, and a link
  that opens that exact point in Google Maps so the host can check it in one
  tap.
- Each row has: approve · edit the value · paste a correct Maps link ·
  skip.
- Rows are sorted so the LEAST confident come first (geocoded before
  link-derived; ambiguous or far-away results before close ones).
- Bulk "approve all above X confidence" is allowed, but nothing is approved
  automatically without the host acting.
- Only approved rows write `distanceMeters` and become visible to guests.

## Guest side

No change beyond what already exists: when a distance is present it appears
first in the card meta line ("1,2 km · Kulinarika" / "850 m · odprto do
22:00"); when absent the card renders without it.

## Verification required

- Report how many of the 73 places resolved from a link, from coordinates,
  from geocoding, and how many failed.
- Show the review list with the least-confident rows first, and prove that an
  unapproved row does not affect the guest UI.
- Prove the manual override survives a recomputation.
- State the exact services called, the rate limits applied, and confirm no
  paid service or key is involved.
- Confirm the tenant's own coordinates are used as the origin — not the
  street address.

## Out of scope

- Live/real-time traffic, walking or cycling profiles (car only for now).
- Recomputing on a schedule; recompute only on change.
- Any bulk write to production without the host approving the rows.
